## 1. 性能弱点清单（W1–W12，按严重度分级）

### 高严重度（构成结构性瓶颈，建议优先处理）

**W1 · 缓存每轮全量重写 + fsync**（`gauge_data/__init__.py:1591-1595` 写入点；`:886-916` merge 逻辑）
每轮刷新无条件把整份缓存 JSON（当前 29.78MB / 394 文件 / 14215 条 records）序列化落盘并 fsync，写入前还整份 `json.loads` 磁盘缓存做 merge。实测热缓存下解析 400ms、序列化 214ms，每轮合计约 1s 纯缓存 IO，且缓存体量随历史无上限增长。优化方向：records 按源文件分片存储；`pending_bytes=0` 且无状态变化时跳过重写。

**W2 · 增量刷新已从 3.8s 劣化到 ~7.3s**（`refresh.py:875` 管线入口；app.log:3722-4063 实测）
9-20 纯 ZCode 时刷新 0.6-1.4s；9-22 Codex 接入后稳态自动刷新 7.2-8.8s（318 次实测）、平台切换 7.6-12.3s——此时 `pending_bytes=0`、`complete=True`，即"增量"名存实亡，每 5 分钟白付一次 7 秒。构成：W1 缓存 IO 约 1s + W3 历史库全扫 1.2s + 13MB JSON 序列化/回读 + node 子进程校验（W12）+ fsync，其余约 5s 为推断缺口。

**W3 · `_read_history` 每轮全表扫描**（`gauge_data/__init__.py:518-569`）
对 thread_items 全表逐行跑 `json_valid`/`json_extract` 提取 18012 条 tools，实测 1193ms/轮，是采集阶段最大单项。sqlite 侧无增量机制，历史库越大线性变慢。优化方向：`item_type` 有值时 WHERE 预过滤；记录水位行号做行级增量。

**W8 · 13.14MB 成品 HTML 内嵌全部明细 + 整页 reload**（`refresh.py:519-547`；`winchild.py:762-767`）
明细数据全部内嵌进单文件 HTML，随历史无上限增长；每次刷新成功 `location.reload()` 整页重读重解析，是面板刷新时延与 WebView 内存尖峰的直接来源。优化方向：数据与壳分离（fetch sidecar 或增量注入），刷新只更新数据。

### 中严重度

**W4 · 日志诊断逐行拉到 Python 聚合**（`gauge_data/__init__.py:630-659`）：55019 行 level/target 拉到 Python 逐行计数，实测 181ms/轮，仅服务 diagnostics 展示。SQL `GROUP BY` 下推可降到毫秒级。

**W6 · 每行 rollout 事件深递归取值**（`gauge_data/__init__.py:1107-1201`）：每行跑 `_find_quota`（深 4 递归）+ 3 次 `_find_scalar`（深 3 递归）。仅解析新字节时付费，但首轮全量百万行级、持续写入时每响应重复付（推断：16.3s 首跑的主要 CPU 构成之一）。优化方向：顶层键快速路径命中后再递归。

**W7 · model_usage 全表 fetchall 双份驻留**（`refresh.py:254-305`）：`fetchall()` 全表行驻留内存，req_raw 再存一份，刷新进程内存峰值随请求数翻倍。改游标流式遍历。

**W9 · 冻结形态托盘进程内联整条管线**（`refreshctl.py:205-234`）：29.78MB 缓存 dict + 快照 dict + 13MB HTML 字符串多份共存于托盘进程（推断：RSS 周期性尖峰）。已知 773MB→33.5MB 修复（`traycore.py:118-125`）无回退风险，但内存峰值风险集中在此。优化方向：冻结形态也走子进程，或分段及时释放。

**W10 · 前端每次渲染 O(N) 全量扫描**（`web/codex.js:167-189, 352-354, 433-454`）：`selection()` 每次 render 全量扫 14215 条 usage + 394 threads，thread 文本 lowerCase 重复算 2 次；`detail()` 每次点开再 2 次全量 filter。当前量级数十 ms 级可接受，数据涨 10 倍会卡顿。优化方向：线程文本预计算、usage 按 thread 预索引。

**W12 · 每轮 spawn node --check 校验脚本**（`refresh.py:165-187`）：对 13MB 成品逐 script 写临时文件并 spawn `node --check`，每轮数百 ms 固定开销。模板未变时可跳过（缓存模板哈希）。

### 低严重度

**W5 · rollout 双指纹无 stat 短路**（`gauge_data/__init__.py:1220-1245`）：每轮对 394 个文件各做 2 次 stat + 2 次开文件读首尾 8KB 算双重指纹，实测 88ms/轮；热缓存零新字节时白付。先比 `mtime_ns`+size，未变跳过指纹。

**W11 · 拖动 mousemove 无节流过桥**（`widget.html:1142`；`winchild.py:531-568`）：拖动期间每个 mousemove 过一次 JS→Python 桥 + WinForms Invoke + SetWindowPos，60-120Hz 下掉帧风险；持久化已有 0.5s 去抖（`winchild.py:593-598`）。mousemove 侧 rAF 合并即可。

### 已核实不构成弱点（避免重复怀疑）

- 前端无重复事件绑定（app 级委托，`codex.js:455-475`、`widget.html:1110-1116`）；无 setInterval 轮询，更新全靠主进程推送。
- 渲染量有界：任务表 30/页、时间线/工具各截 100、排行 12、Agent 树 60 根；widget 仅 8 任务 + 7 柱 SVG。
- `_dedup`/`_finalize_usage` 均 O(N) 带索引（实测 63ms）；`_CACHE_LOCK` RLock 1.2s 超时 + 文件锁让路，无死锁面；单实例刷新锁防重入有效。

## 6. 可升级性评估

- **第三平台接入成本（已收敛但有不对称）**：平台闸门是 `config.PLATFORMS` 元组；平台无关接口面（platform bundle、is_valid_platform、_decorate_widget）已就位。新增平台需：新采集模块 + PLATFORMS 扩一项 + 两侧 UI 选项 + sidecar 键 + widget.html 平台分支 + CSS 前缀分支。主要不对称：**gauge_data 只有 collect_codex，ZCode 采集内联在 refresh.py:797**——第三平台时应先抽 `collect_zcode` 进包对齐形态。
- **平台硬编码分布**（rg 实测密度）：数据层 Codex 集中（gauge_data 为 Codex 专属）、ZCode 集中于 refresh.py（×30）；桌面层散点（refreshctl 分支 ~6 处、widget.html:819 校验、winchild `_open_codex_quota`）；前端 widget.html codex×85（含 36 处 codex-mode 前缀，与验收台账 §2.4 声明一致）。
- **预留扩展**：OAuth 实时额度端点未接（当前从 rollout 挖 quota + 跳官方网页），与"后续增强、须标注 app_server 来源"的规划一致，接入时按 docs/阶段0 探针结论实施即可。
- **升级回退**：回退件为手工目录（O13 风险）；安装器版本三处硬编码（O12）；缓存不兼容自动重建路径完整。

## 8. 方法与局限

- 本报告由三个并行只读 Luna 分片采集、主代理抽查关键声明后整合；抽查证实的声明已在文中标注"（已复核证实）"。
- 分片间未重叠写入（全部只读），互证点：双链常数、缓存版本机制、codex-mode 前缀隔离三处由两个以上分片独立确认一致。
- 局限：未实际运行整条 refresh（会写产物，越只读边界）；7.3s 中约 5s 的精确构成为推断；模板注释与复制粘贴检测为启发式，未逐行人审全部 1.1 万行；exe 与 iss 版本一致性未做运行时核验；首跑 16.3s/增量 3.8s 的原始记录（PROJECT_STATE）未在仓库内找到，性能基线以 app.log 实测为准。
- 性能数字的环境：本机 394 rollout 文件 / 29.78MB 缓存 / 14215 条 usage / 55019 行日志；更大历史下的劣化斜率为推断。
